# LLM / 检索质量回归评测

**定位：防退化，不是精度验证。**

实测同一份简历连跑 4 次，文化契合给出 72/72/58/58——**数值本身就不稳定**。
所以这里只断言**硬性不变量**：

- 该出现的字段出现了吗（`skills` / `education` / `missing_skills`）
- 结构类型对吗（列表还是字符串、分数是不是数字）
- 文化评语**真的引用了该 JD 的原文价值观**吗（还是退回了写死的通用价值观）
- 未设限的维度**没有被当成 0 分**写进决策理由吗

分数、耗时、token、成本**全部只记录不判定**，多次运行看分布趋势由人工判断。

## 两层评测，分管不同的变量

这个项目里有**三条互不影响**的链路，改动落在哪条上就归哪层管：

| 层 | 链路 | 受哪些变量影响 | 运行器 | 门禁 |
| --- | --- | --- | --- | --- |
| **L1 招聘评分** | `workflow/recruitment_graph` | chat 模型、提示词、权重、门限 | `run_eval.py` | 手动触发 |
| **L2 知识库检索** | `rag/knowledge_base` | **chunk 策略**、embedding 模型 | `run_chunk_eval.py` | 日常 CI |
| **L3 简历分段** | `services/resume_cleaner` | `segment_text` 策略 | `tests/test_resume_cleaner.py` | 日常 CI |

**招聘评分链路完全不调用 embedding**（`src/workflow` 下无任何 embedding 调用），
所以「换 chat 模型」和「换 embedding 模型 / 改 chunk 策略」必须分开测——
前者用 L1，后者用 L2。

## RAG 链路本轮修复了什么（先看这个）

做这轮评测时实测发现：原实现里的「混合检索」是**假的**。`_retrieve_docs`
先把 BM25 结果全部塞进列表、再把向量结果追加到后面，最后 `merged[:k]` 截断；
而 `BM25Retriever` 的 k 就是 4，且它对**任何**查询都回满 4 条（连「今天股市行情如何」
这种完全无关的问题也回 4 条）——列表在轮到向量结果之前就已经满了。

后果是：向量库照建（每次重建还要重嵌全库、花 embedding 成本），线上却一条都不读；
`mode` 还照报 `hybrid_rag`，标签会骗人。**换 embedding 模型对检索结果零影响**，
任何针对它的回归测试都是假信号。

本轮修复：

| 修复 | 位置 | 守门测试 |
| --- | --- | --- |
| **RRF 融合**：两路各自取候选、RRF 融合后截断，向量真正进入上下文 | `knowledge_base._rrf_fuse` | `tests/test_rag_fusion.py` |
| **mode 如实反映参与的路数**：`hybrid_rag` / `bm25_llm` / `vector_llm` | `knowledge_base._retrieval_mode` | 同上 |
| **索引口径指纹**：embedding 模型+维度+切分参数写进 collection metadata，不一致就重建 | `knowledge_base._index_fingerprint` | `TestIndexFingerprint` |
| **索引一致性**：条数与当前切分结果对不上就重建（原先新增系统文档只进 BM25、不进向量库） | `init_knowledge_base` | `TestIndexConsistency` |
| **中文分词加字符 bigram**（见下） | `knowledge_base._tokenize` | `tests/test_kb_tokenization.py` |
| **重排（rerank）**：交叉编码器对候选逐条精排，可开关可降级 | `knowledge_base._rerank` | `tests/test_rag_rerank.py` |
| **检索埋点**：query、各路命中、耗时、口径落库 | `services/retrieval_log` | `tests/test_retrieval_log.py` |

### 实测：三条检索路径的消融

同一套 13 条词面用例 + 5 条语义改写用例，chunk_size=500：

| 路径 | 词面用例 Top-1 | 词面用例 MRR | 语义用例 Top-1 | 语义用例 MRR |
| --- | --- | --- | --- | --- |
| BM25 only | 0.7692 | 0.9167 | — | — |
| 向量 only | 0.9231 | 1.0000 | 0.6000 | 0.7500 |
| 混合（RRF） | 0.9231 | 1.0000 | 0.6000 | 0.7500 |
| **混合 + 重排** | **0.9231** | **1.0000** | **1.0000** | **1.0000** |

两个反直觉但重要的结论：

1. **向量路单独就达到了混合检索的最好成绩**，BM25 在这套用例上反而拖后腿
   （词面用例 Top-1 0.7692 vs 0.9231）。保留 BM25 的理由不是"它更准"，
   而是**精确字面串的兜底**（产品名、人名、编号这类向量容易混淆），
   以及它**零额外成本**（不需要 embedding 接口）。
2. **重排的收益全在语义改写用例上**（Top-1 0.6 → 1.0，+40pp）；
   词面用例已经在天花板，重排对它们没有任何改变。

### 实测：chunk_size 选型

混合检索路径下，200 / 300 / 400 / 500 / 800 的 MRR 与 Top-1 几乎一致
（300 略低 1 条）。**chunk_size 在这个区间内对排序质量无实质影响**，
所以保持现值 500 不动——没有证据支持改，也就不该改。


### 为什么分词要加 bigram

jieba 的切分是**上下文相关**的，同一个词在查询与文档里会被切成不同形状：

```
查询「每月什么时候发工资」 → ['每月','什么','时候','发工资']
文档「每月15日发放上月工资」 → ['每月','15','日','发放','上','月工资']
交集：{'每月'}   ← 「工资」完全对不上
```

这不报错也不崩溃——检索照样返回 4 条，只是排序毫无意义。当时那条用例是
**靠并列排序的运气**通过的（BM25 对全零分查询照样回 Top-K），不是靠真实相关。

加上字符 bigram 后，「工资」在两边都作为 bigram 出现，匹配恢复。
副作用是无关查询的分数也会上升（实测 0.616 → 2.540），这是接受代价：
bigram 的 IDF 很高（几乎只出现在一处），偶然共现权重极低。

修完之后 **chunk_size 的安全下界问题也一并消失了**——原先 200/300 会让
`11-薪资保密` 失效，现在 200~800 全绿（因为命中靠的是高 IDF 的 bigram，
不再取决于「工资」这个词恰好落在哪个块里）。

> **事后修正（以分阶段消融为准）**：上面这段是在**"向量路是死的"**前提下测的。
> 补上对照格（jieba 分词 + RRF 融合）后重新测，结论变了：
> - 向量路生效后，**两种分词在 200~800 全部 13/13 通过**——
>   安全边界已由"向量路是否生效"决定，不再由分词决定；
> - 只改分词（RRF 不变）时，**硬判据无变化**，语义组 Top-1 反而后退 1 条用例
>   （0.8000 → 0.6000），而收益只有 chunk_size=200 极端档位上的 +7.7pp。
>
> 也就是说 **bigram 不是本轮收益的来源**（来源是"让向量路生效 + RRF + 重排"），
> 它是否值得保留属于**待决策项**：n=18 太小分不清噪声还是真负收益，
> 需要真实生产流量重测后再定。详见 [`检索调优报告.md`](../../检索调优报告.md) 第 4.3 节。

## L1：招聘评分层

### 运行

```bash
# 全部用例
python tests/eval/run_eval.py

# 只跑指定用例（名称子串匹配）
python tests/eval/run_eval.py --cases 01 07

# 每条跑 3 次，观察数值波动
python tests/eval/run_eval.py --repeat 3

# 导出 JSON 报告
python tests/eval/run_eval.py --out report.json

# 与基线报告对比，判定退步
python tests/eval/run_eval.py --baseline last_report.json --out report.json
```

**需要 `.env` 配置真实 LLM / embedding 凭据**——本运行器不 mock 模型，
mock 了就测不出真实退化。因此会产生真实 API 成本，**不进日常 CI**，
只在手动触发的工作流里跑。

### 怎么加用例

在 `cases.json` 的 `cases` 数组里追加一项：

```json
{
  "name": "23-新场景",
  "resume_ref": "resumes/xxx.pdf",     // 或用 "resume_text": "内联文本"
  "jd_ref": "jds/xxx.txt",
  "position": "岗位名",
  "assertions": [
    {"kind": "education_not_empty", "note": "为什么加这条"}
  ]
}
```

素材放 `resumes/` 或 `jds/` 下，`resume_ref` / `jd_ref` 用相对该目录的路径。

### 可用的断言类型

| kind | 判据 | 拦的是什么 |
| --- | --- | --- |
| `key_present` | 结果含指定键（配 `node` + `keys`） | 结构化解析整体失效 |
| `education_not_empty` | 简历写了学历时必须解析出学历 | `parse_resume` 被跳过（历史 bug：`raw_text` 快照被误判为已解析） |
| `type_is_list` / `type_is_number` | 字段类型正确（配 `node` + `field`） | 模型输出结构漂移 |
| `culture_cites_jd` | JD 有 `culture_values` 时评语必须引用其中至少一个 | 退回写死的通用价值观 |
| `missing_skills_shape` | `matched_skills` / `missing_skills` 都是列表 | 逐条核对机制失效 |
| `no_zero_risk_for_unconstrained` | 未设限维度不得在决策里被写成 0 分 | 未设限维度被当 0 分（历史 bug） |
| `decision_shape` | decision 属于 `推荐录用/待定/不推荐/待人工复核` | 决策被污染或流程崩溃 |
| `faithful` | 回答里的事实能在本次检索到的片段里找到出处 | RAG 编造（"知识库没有的内容不许编"终于有门禁了） |

断言实现见 `run_eval.py` 的 `ASSERTIONS` 字典。**新增断言时只判断"不变量是否成立"**，
不要写数值区间——那样会因为模型波动频繁误报，最后没人看。

### 知识库忠实度用例（`kind: knowledge`）

招聘评分用例与知识库用例走**两条不同链路**，用 `kind` 区分：

| kind | 链路 | 断言对象 | 用例数 |
| --- | --- | --- | --- |
| 缺省 | 简历 + JD → 招聘评分 | 各维度不变量 | 22 |
| `knowledge` | 问题 → 知识库检索 → LLM 回答 | **答案里的事实有没有出处** | 4 |

知识库用例的做法有个关键点：**检索片段、送给 LLM 的上下文、比对素材三者
必须来自同一次检索**。不能直接用 `_query_sync` 返回的 `sources`——那里的
`content` 被截断到 200 字，而 LLM 看到的是完整 chunk，拿截断素材比对会
凭空产生误报（模型引用了 200 字之后的内容，素材里却没有）。

忠实度判定逻辑在 `faithfulness.py`，分层是：**数字类硬断言**（要么原文出现
要么就是编的）、**制度名/条款号宽松匹配**、**自由文本只记录不判定**
（「回答里出现上下文没有的普通名词」无法区分常识补充与编造，硬判必误报）。

### 口径指纹与基线对比

报告里会记下这次的**口径**——决定「两次结果能不能直接比」的那几项：

| 字段 | 含义 | 变了意味着 |
| --- | --- | --- |
| `code_digest` | 评分模块源码摘要（提示词/权重/门限） | **评分口径变了**，与模型无关 |
| `config_digest` | 运行时配置摘要（模型名/base_url/temperature/timeout） | **换模型了**——换模型时这是预期变化 |
| `embedding_model` / `kb_chunk` | 知识库侧口径 | 记录下来只为说明「这次到底变了什么」 |

`--baseline` 对比分两类判定：

1. **断言退步（硬）**：某条硬性不变量从 PASS 变 FAIL → 计入失败退出码。
2. **分数漂移（软）**：维度中位数相对基线移动超阈值（默认 ±10）→ **只提示，不计入退出码**。

分开是刻意的：大模型采样本身不可复现，把波动写成门禁只会天天误报，最后没人看。

## L2：知识库检索层（chunk 策略 / embedding 模型）

### 运行

```bash
# 按当前生效参数跑一遍（离线 BM25，无网络、无成本）
python tests/eval/run_chunk_eval.py

# 指定参数
python tests/eval/run_chunk_eval.py --chunk-size 300 --chunk-overlap 50

# 参数 sweep：找出策略的失效边界
python tests/eval/run_chunk_eval.py --sweep

# 启用向量检索（需要 embedding 凭据，产生真实 API 调用）
python tests/eval/run_chunk_eval.py --vector

# 启用重排（需要 rerank 凭据；默认复用 embedding 那一套网关）
python tests/eval/run_chunk_eval.py --vector --rerank

# 导出 JSON 报告
python tests/eval/run_chunk_eval.py --out chunk_report.json
```

**这个运行器可以进日常 CI**：BM25 路径全在本进程内算，无网络、无成本、结果可复现。
日常门禁已经由 `tests/test_chunk_strategy.py` 接进 pytest。

### 为什么必须 sweep，而不是只测当前参数

实测：当前 `chunk_size=500` 时，6 篇制度文档（309~460 字）**各自正好切出 1 块**——
切分是空操作，改成 600 或 800 对检索结果毫无影响。
只测当前参数等于什么都没测，会得到一个必然全绿的假信号。

sweep 把参数往下压，逼出策略的真实失效边界：

```
  chunk_size  overlap  结果     失败用例
         200       50  PASS   -
         300       50  PASS   -
         400       50  PASS   -
         500       50  PASS   -
         800       50  PASS   -
         500        0  PASS   -
         500      100  PASS   -
         500      150  PASS   -
```

（分词加 bigram 之前，200/300 会让 `11-薪资保密` 失效——见上文。）

### 断言了什么

1. **切分不变量**（与策略无关，任何参数下都必须成立）
   - 文档全覆盖：每篇源文档至少切出 1 块，没有整篇丢失
   - 长度上界：没有块超过 chunk_size
   - 内容不丢：原文去空白后是切块拼接结果的**子序列**（顺序也不许乱）
   - 元数据完整：每块都带 title / source

2. **检索命中**（每条黄金用例，见 `chunk_cases.json`）

| 字段 | 判据 | 拦的是什么 |
| --- | --- | --- |
| `expect_titles` | 期望文档标题必须出现在 Top-K | 该召回的没召回 |
| `expect_terms` | 期望词必须出现在**同一个**块里 | 跨块事实被切断——LLM 只看得到被检索到的块原文，跨块的事实它根本看不见 |
| `expect_absent_terms` | 这些词一个都不该出现在结果里 | 语料被污染（比如有人粘进无关制度） |
| `requires: vector` | 该用例只在 `--vector` 模式下评估 | 语义改写类查询，词面重叠太低，混进离线门禁只会天天误报 |

**为什么不断言"不该召回某文档"**：langchain 的 `BM25Retriever` 没有分数阈值，
`get_top_n` 对全零分的查询照样回 Top-K——这种断言恒假，只会天天误报。
「知识库没有的内容不许编」这个保证在 **LLM 层**（提示词 + 忠实度断言），
不在检索层。

### 报告里会给出什么

```
索引统计：6 篇文档 / 6 块 / 均长 359.7 字（最短 309，最长 460） / 空块 0 / 重复块 0

排序质量（只记录，不参与判定）：
  MRR=0.9167  recall@4=0.9231  Top-1 准确率=0.7692
```

- **索引统计**：改切分策略时最先要看的数字。块数突然翻倍 = 切碎；骤减 = 切粗。
  空块与重复块进了索引却永远召不回，纯属污染。
- **MRR / recall@k / Top-1 准确率**：回答"排得靠不靠前"，而不是"有没有命中"。
  **只记录不判定**——排序抖动在大模型参与时本就存在，写成断言会被误伤。

### 怎么加用例

在 `chunk_cases.json` 的 `cases` 数组里追加：

```json
{
  "name": "19-新问题",
  "query": "用户在 HR 问的问题",
  "expect_titles": ["员工福利制度"],
  "expect_terms": ["同块必须一起出现的词"],
  "note": "为什么加这条"
}
```

### 从生产流量长出用例

手写的黄金集会随时间失真：真实用户问的问题跟写用例时脑子里想的不一样。
而真实问句**已经在库里了**——`retrieval_logs` 记着每一条。

```bash
# 取问得最多的前 50 条，生成候选
python tests/eval/mine_traffic.py --limit 50 --out traffic_candidates.json

# 没有生产流量时，用内置模板验证工具链本身
python tests/eval/mine_traffic.py --demo --out traffic_candidates.json
```

模板问句是**刻意**用与制度原文不同的说法写的（"能休几天假" vs 原文的"年假"），
所以按 0.25 的阈值它们大多会落进人工队列——这正是预期行为，
说明工具没有硬凑标签。demo 的作用是验证**工具链本身**跑得通：
读得到问句、给得出候选、标得出重叠度与置信度、产出恒为 `reviewed: false`。

**关键设计：标签必须独立于检索。** 绝不拿"当前检索排第一的文档"当标签——
那是自证：检索错了标签也跟着错，评测就永远发现不了问题。这里的建议标签来自
**纯文本比对**（问句与源文档的字符 bigram 重叠度），与 BM25 / 向量 / 重排
任何一环都无关，是对流水线的独立交叉检查。

注意独立性的来源是"**比的是源文档原文、从不查检索结果**"，不是"关掉 embedding"。
`current_hits`（当前检索实际召回了什么，给人参考）走的是**生产的混合检索路径**，
让人看到的是线上真正会返回什么。

即便如此，产出仍是**候选**而非既成用例：每条带 `reviewed: false`，
需要人确认后才并进 `chunk_cases.json`。

### 自动标注到底有多准（实测，不是拍脑袋）

拿 16 条真实感问句（口语化、错别字、省略主语、与知识库无关的闲聊）
跑过一遍自动标注：

| 阈值 | 自动标注 | 标对 | 准确率 | 覆盖率 |
| --- | --- | --- | --- | --- |
| 0.08（原来的默认） | 13 | 10 | 76.9% | 81.2% |
| 0.20 | 10 | 9 | 90.0% | 62.5% |
| **0.25（现在的默认）** | **7** | **7** | **100%** | **43.8%** |

所以默认阈值从 0.08 提到 **0.25**：标的时候要标对，标不准的一律交给人。
理由是**错误的标签比没有标签更糟**——有标签会锚定复核的人，让人先接受再纠正；
没有标签只是多花点力气自己选。

配套两条规则：
- **并列最高就拒标**：两篇制度的文本重叠度打平，说明从文本上分不出该归哪篇，
  随便挑一篇等于凭空造标签（实测"新人培训多久"就在培训制度与入职流程之间打平）。
- **候选带领先幅度与置信度**：领先幅度小于 0.1 的标为低置信度，优先人工看。

这个阈值是**从 16 条样本上量出来的，不是通用常数**：真实流量积累后要重新校准
（用 `--min-overlap` 临时调）。

## 换模型做回归的标准流程

1. 改模型配置（界面或 `llm_config.save_config`）
2. 跑 `python tests/eval/run_eval.py --repeat 3 --out report.json`
3. 拿上一次的报告当基线：`python tests/eval/run_eval.py --baseline last_report.json --out report.json`
4. 看对比输出里的三块：
   - **口径变化**：`config_digest` 变是预期的（换模型了）；`code_digest` 也变说明提示词/权重被一起动了，
     **分数差异无法归因到模型效果**，必须分开评
   - **断言退步**：硬判据，有就是退步
   - **分数漂移**：方向性参考，采样有波动，别当精确结论

换 **embedding** 模型则改用 L2：`python tests/eval/run_chunk_eval.py --sweep --vector`。
注意 embedding 模型换掉后向量维度会变，知识库会自动检测到口径不一致并重建索引
（`knowledge_base._index_fingerprint`，原目录备份为 `.bak-<时间戳>`）。
**同维度换模型也一样会重建**——原先只探测维度，换成同样 1024 维的另一个模型会静默复用旧向量。

换 **rerank** 模型不需要重建索引（向量本身没变），但仍要用 L2 回归确认收益还在：
`python tests/eval/run_chunk_eval.py --vector --rerank`。
注意重排模型**不在索引指纹里**（`_index_fingerprint` 只管 embedding 与切分），
所以换 rerank 模型不会被自动检测出来，得自己记得在评测里跑一遍。

## 设计取舍

- **为什么不断言具体分数**：数值不可复现，锁死会天天误报，最终被无视。
  要提升稳定性应该从「固定模型版本 + 人工复核区间」入手，而不是把不稳定的数值写成断言。
- **为什么 L1 不进日常 CI**：每次全量评测要跑几十次真实 LLM 调用，有固定成本；
  且结果含随机性，不适合作为每次 push 的门禁。手动触发更符合实际使用节奏。
- **为什么 L2 能进日常 CI**：BM25 路径无网络、无成本、可复现，秒级完成。
- **为什么用 RRF 而不是加权求和**：BM25 分数无界、余弦相似度 0~1，量纲不同；
  加权必须先归一化，而归一化对语料敏感。RRF 只看名次，天然免疫量纲差异。
- **为什么用 JSON 而不是 YAML**：少一个依赖（项目未引入 pyyaml），
  且断言结构简单，JSON 足够表达。

## 本轮验证到了什么程度

评测体系自己不会校验自己，所以另外做了一轮"验证这套验证"的实跑。
四项之前标着"未验证"的东西，这轮都验了——**两个真缺陷因此被发现并修掉**，
还有一个问题验出来了但**没动代码**（需要你拍板）。

| 之前未验证的 | 怎么验的 | 结果 |
| --- | --- | --- |
| L1 招聘评分没跑过真实 LLM | 用 `.env` 的真实凭据跑全量 26 条 | 首次实跑 **19/26 通过**，7 条失败全部归因到下面缺陷 ③（预算墙误拦）与缺陷 ④（断言模块压根没加载起来）；修完后**复跑那 7 条 → 7/7 通过**，合起来 26/26 |
| `--vector` / `--rerank` 的 CI lane 没在 CI 上跑过 | 按 CI 的形态本机复现：清掉 `.env`、只给环境变量、跑 ci.yml 里的原命令 | 18/18 通过，重排确实生效；**并因此发现缺陷 ①** |
| 迁移只在 SQLite 上验过 | 起隔离的 postgres:16-alpine 容器跑 `alembic upgrade head` | 7 步迁移链干净通过；16 张表与模型**零漂移**；`downgrade base` → `upgrade head` 往返后仍无漂移；`retrieval_logs` 真实写入回读正常 |
| 流量挖掘只在 `--demo` 模板上验过 | 16 条真实感问句 → 真实检索 → 真实 `retrieval_logs` → 挖掘 | 自动标注 7 条**全对**；**并因此发现缺陷 ②** |

### 缺陷 ①（已修）：重排被静默跳过，报告却显示"全绿"

GitHub Actions 对**未配置的 secret 传空串**（不是"不设置"）。空串会让
`_build_reranker()` 返回 None ——而且**不报错**：重排根本没跑，
但检索照常返回结果、断言照常全绿，报告读起来像"重排验证通过"。

这是评测体系自己的盲区：**它没法区分"重排跑通了"和"重排压根没跑"**。
现在传了 `--rerank` 却没重排成功会判失败并让退出码变成 1，
报告里多一段 `rerank_check` 说明"请求了但没生效"。
CI 那边另加 preflight：secret 缺失时 1 秒内失败并点名变量。

### 缺陷 ②（已修）：`current_hits` 不是生产路径的结果

标注阶段把 embedding 关了（当初的意图是"保证标注独立于检索"），
于是连给人参考的"当前检索命中了什么"也退化成 BM25-only——
线上实际是混合+重排，人拿它当参考会看错。

标注的独立性其实来自"**比的是源文档原文、从不查检索结果**"，与关 embedding 无关。
两者分开之后：`current_hits` 走回真实的混合检索路径，标注仍然是独立的。

### 缺陷 ④（已修）：忠实度断言模块**从来没真正加载过**

第一次拿真实 LLM 跑 L1 时，4 条知识库忠实度用例全部报同一句话：

```
✗ faithful: 断言执行异常: 'NoneType' object has no attribute '__dict__'
```

那句"断言执行异常"把真因盖住了。追下去是**导入期**就炸了：

```
File "tests/eval/faithfulness.py", line 205, in <module>
    @dataclass(frozen=True)
    ns = sys.modules.get(cls.__module__).__dict__
AttributeError: 'NoneType' object has no attribute '__dict__'
```

`run_eval` 用 `importlib` 按路径动态加载忠实度模块（脚本方式运行时
`tests/eval` 下没有 `__init__.py`，普通 import 不可用），
而**动态加载出来的模块默认不在 `sys.modules` 里**；
`@dataclass` 在类定义完成时要回查 `sys.modules[cls.__module__]`，
回查拿到 None 就抛上面那个异常。

后果比看上去严重：异常发生在导入期 → 整个模块加载不起来 →
每条用例都只报"断言执行异常"。看上去像"断言不通过"，
实际是**断言压根没跑过**——一个不会自己冒头的静默故障。
`tests/test_faithfulness.py` 里那 58 项测的是**正常 import 路径**，
所以一直没暴露。

修法：动态加载后先 `sys.modules[spec.name] = module` 再执行模块
（importlib 动态加载的标准做法），失败时清理注册。
新增 4 项测试守住这个加载路径，其中一项专门断言
"凭空编的数字必须被抓住"——确保它真的在判定，而不是在报错。

**实跑代价**：这条缺陷让知识库忠实度断言**从未真正执行过**——
`tests/test_faithfulness.py` 的 58 项测的是正常 import 路径，
所以一直没暴露；而 L1 走的是动态加载路径。一句话：
**同一份代码，两种加载方式，一种能跑一种不能跑，而只有后者被评测用。**

### 缺陷 ③（已修）：预算墙把同一笔钱算了两遍，¥5 的上限只用了 57% 就触顶

跑全量 L1 评测时撞上的：预算墙（配置上限 ¥5/日）在**真实花费 ¥2.84** 时就触发了。
把数字摊开看——

| 口径 | 数值 |
| --- | --- |
| 落库成本（101 次真实调用） | ¥2.8362 |
| 预算墙读到的数 | ¥5.6724 |
| 配置的上限 | ¥5.00 |

**正好是 2 倍。** 根因在 `budget.spent_in_window()`：回读时返回
`库内总额 + 进程内累计`，而每次调用都会立刻落库——库里的数字**已经包含**
本进程那部分，再加一次就是同一笔钱算两遍。更糟的是回读分支从不让进程内累计归零，
进程跑得越久重复的部分越大。

顺带发现的**第二个洞**：非回读分支直接 `return _spent`（只看进程内累计），
把历史与其它进程的花费全漏了。默认每 20 次才回读一次，
也就是 20 次里有 19 次的预检几乎形同虚设——今天已经花超上限照样放行。

修法：落库是唯一事实源，窗口总额 = 上次回读到的库内总额 + 回读之后本进程新增的，
回读时把已落库的部分从进程内累计里扣掉，两者不再重叠。
新增 `tests/test_budget_accounting.py`（5 项）钉住这个口径；
**这批测试在旧实现下有 3 项是红的**（验证过：临时还原旧代码跑一遍确认过）。

### 已拍板并实施：`LLM_TIMEOUT_SECONDS` 不是单次调用的耗时上限

`llm_json` 用的是 `timeout=45` + `max_retries=2`。timeout 是**每次 HTTP 请求**的，
最多 3 次尝试，于是单次逻辑调用的最坏耗时 ≈ 3 × 45s。实测（本地起一个
"接受连接但永不回应"的服务端，让每次尝试都耗满超时）：

| max_retries | 实测耗时 | 理论 |
| --- | --- | --- |
| 2 | **136.4s** | 135s |
| 1 | 90.5s | 90s |
| 0 | 45.0s | 45s |

真实跑批里也观测到一次 136s 的成功调用，与理论吻合。

后果：招聘流水线一条简历要**串行**调 ~8 次 LLM，最坏单请求 ≈ **18 分钟**，
远超前端/网关的超时——用户看到的是网关报错，后台还在按次计费。
而且超时后的降级是"改用规则模板算分"，分数与 LLM 算出来的**长得一样**。

**已实施的决定**（用户拍板）：timeout 45 → **90 秒**，max_retries 2 → **1**。

理由不是"重试总是坏"，是两条实测数据：

1. **`parse_job_description` 的延迟是双峰的**：p50 只有 4.2 秒，但 p90 高达 86.6 秒、
   峰值 136.4 秒（507 次真实调用）。因为它要输出 8000+ tokens。
   45 秒的超时会把"只是慢、其实能成功"的调用**误判成失败**——
   实测该环节的失败率 2.74%（2/73），而其它环节全是 0%。
2. **重试是全损重来**：同一 prompt 在推理型模型上再次超时的概率很高，
   于是前两次烧掉的 token 白花，延迟也翻三倍。11/507 = 2.2% 的调用单次耗时
   >45s，它们额外多烧了 22 次尝试。

改完后：单次逻辑调用最坏从 135s → 90s，慢任务不再被误杀，无效重试少一半。

**注意**：`LLM_TIMEOUT_SECONDS` 在 `.env` 里显式写的是 45，而环境变量优先级高于
代码默认值——只改 `config.py` 不会有任何效果。`.env` 必须同步改成 90。
（`.env` 不进版本库，所以换机器部署时别忘了。）

`LLM_MAX_RETRIES` 走代码默认值 1，可用环境变量覆盖。

**仍然没验到的**：真实 GitHub runner 上没跑过 CI lane（需要仓库权限）；
真实生产流量仍然没有——上面那 16 条是按真实脏度手写的问句。

## 任务成功率评测（L3：整条工作流）

前两层测的是"检索效果"和"答案质量"，这一层测的是**整条招聘工作流能不能跑完**。

### 为什么不能只靠真实跑批

实测（本地 507 次真实 LLM 调用）：调用层成功率 99.61%，但**任务层几乎没有
可观测的失败样本**——本地库里只有 3 条 `workflow_runs`，n=3 算不出任何东西。

而真实跑批的失败率太低：N=15 的真实任务期望失败 0.06 次，
**测改进前后有没有差别，等于什么都没测**。

所以主实验必须用**可控故障注入**：在指定节点注入指定故障，
n 可控、归因明确、零 API 成本、同种子可复现。

### 三个工具

```bash
# ① 注入实验：mock 掉最底层的 LLM 调用，按故障模式定点注入
python tests/eval/task_success_eval.py --n 20 --include-control \
       --out task_success_before.json

# ② 真实任务：不 mock，端到端跑真 LLM，量终态/耗时/花费
python tests/eval/task_success_real.py --n 15 --out task_success_real_after.json

# ③ 前后对比
python tests/eval/task_success_compare.py before.json after.json
```

### 注入点为什么选 `_invoke_raw`

`src/services/llm_invoke._invoke_raw` 是所有 LLM 调用的最底层。
在它上面打桩，意味着 `invoke_json` 的**降级、埋点、预算检查、熔断全是真实生产代码**，
不是我们在评测脚本里模拟出来的。注入点选高一层（比如 mock 整个 `_llm_json`），
测的就是我们自己写的那套 mock。

### 六种故障模式

| 模式 | 注入方式 | 改前的行为 |
|---|---|---|
| `timeout` | 抛 APITimeoutError | invoke_json 降级到 default，任务继续 |
| `upstream_5xx` | 抛带 500 的异常 | 同上 |
| `bad_json` | 返回非 JSON 内容 | JsonOutputParser 失败 → 降级 |
| `bad_schema` | 合法 JSON 但字段类型不对（`score: null`） | **节点 `float(None)` 崩 → 整任务死** |
| `db_error` | 在写库那一刻抛异常 | **整任务死** |
| `budget_exhausted` | 抛 BudgetExceeded | 转人工 budget_halted（本来就对） |

### 三个指标（都给分子/分母，不给孤立小数）

- **存活率**：任务没被异常打断（终态 ∈ {waiting_human, completed, budget_halted, partial}）
- **干净率**：全程无任何维度使用兜底分（结论完全来自模型）
- **有结论率**：存活且库里确实落下了维度评分（结论可用）

外加 **部分有用率**：任务没跑完但库里仍留有已评估维度（沉没成本）。

### 两个必须守住的有效性守卫

1. **对照组必须全绿**（不注入时存活率 = 1.000）。低于 1 说明工具本身坏了，
   后面的对比全无意义。
2. **注入必须真的命中**（`injection_missed == 0`）。不命中时工具会打
   `<-- 注入未命中(harness 失效)`，不能静默算成"注入后任务仍然存活"。

这两个守卫是被真实踩出来的：`parse_resume` 节点是**幂等**的
（读 `resumes` 表判断是否已结构化解析），而清理不彻底时 SQLite 会复用候选人 id，
下一个场景就读到上一轮的残留、**跳过 LLM 调用**——注入永远打不中，
评测假绿成"注入无效"。此外 `required_skills` 必须是 dict 列表
（`{"skill": ...}`），写成字符串列表会抛 `'str' object has no attribute 'get'`。

## 已知未做 / 不可行的项

诚实记下来，免得下次有人当成"漏了"或者"能做"：

- **BM25 相关性下限没做**（原 P2 计划）。实测过：用 BM25 原始分数设阈值在这份语料上
  **分不开合法与无关查询**——合法查询最低 1.042（"每月什么时候发工资"），
  无关查询却能到 4.494（"怎么申请调岗"命中了福利制度里的"申请流程"）。
  设阈值要么砍掉合法召回，要么放过无关查询，两头不讨好。
  相关性判断目前交给 LLM 层（提示词 + 忠实度断言）承担。
  要做的话得走**向量相似度**阈值，而不是 BM25 分数。
- **检索的 recall@k / nDCG 只做了 Top-K 命中与名次**，没做严格的相关性分级标注
  （每条查询标"哪几块算相关"）。缺这份标注，nDCG 算不出来。
- **增量更新没做**：新增/删除自定义文档仍会触发全量重建（重嵌全部文档）。
  语料小的时候可接受，语料大了成本会线性上升。
- **延迟/并发 SLO 没有用例**：需要压测环境，不适合放进日常 pytest。
- **L1 的忠实度断言**（`faithfulness.py`）只在离线用例上验证过，
  真实 LLM 生成的答案还没跑过——那需要凭据且有成本。
- **检索埋点目前只覆盖走 RAG 路径的问答**。`_query_sync` 在 `_qa_chain is None`
  时会直接走规则模板、**不落检索日志**——那条路径没有发生向量/BM25 检索，
  落的是 `keyword_search` 的规则命中。生产上 LLM 一定启用，所以影响有限；
  但如果要把"所有用户提问"都收进评测集，得把兜底路径也记上。
- **离线建库时的 embedding 成本/耗时仍无处落库**：检索埋点记的是查询侧的
  `vector_ms`，批量 embedding 的开销要另加列 + 另加一个迁移。
- **检索日志的 `query_text` 可能含员工姓名**，目前只靠 90 天保留期兜底，
  没做字段级脱敏。若合规要求更严，得在写入前做 PII 识别与替换。
- **`top_queries` 没有 HTTP 端点**，目前只能作为库内函数调用；
  要让前端看到"问得最多的问题"需要另加一个接口。
- **建库方式有个坑没堵死**：用 `Base.metadata.create_all()` 建的库
  是"表齐全但没有 alembic_version"，`migrate_database()` 会把它当旧库
  stamp 到基线，随后基线之后的迁移重复加列而失败。
  现在失败信息会直接说明这一点并给出两条出路（删库重建 / 手工 stamp head），
  但**根因没堵**——它依赖"旧库结构 == 基线"这个假设，
  真正的修法是建库时统一走 alembic。
- **离线建库的 embedding 成本、批量重排成本仍无处落库**（本轮补了查询侧，
  批量侧还没动）：单次检索的 `vector_ms` / `rerank_ms` 有了，
  但"重建一次索引花了多少钱"没有任何记录。
- **重排是同步阻塞的**：rerank 请求直接串在检索链路里，超时上限 10s
  （`min(LLM_TIMEOUT_SECONDS, 10)`）。最坏情况下一次查询要多等 10s 才降级。
  没有超时自适应、没有并行化、没有按请求粒度的熔断，只有全局开关 `RERANK_ENABLED`。
  真要上生产，10s 的尾延迟比它带来的排序收益更值得先担心。
- **重排的口径没进指纹**：`_index_fingerprint` 只记 embedding 模型/维度/切分参数，
  **不含 rerank 模型**。换 rerank 模型本来也不该重建索引（向量没变），
  但评测报告会分不清「是重排模型变了还是代码变了」——
  `code_digest` 能兜住一半，另一半（rerank 模型名）目前无处记录。
- **重排降级只有一个布尔位**：`rerank_applied=False` 表示「没重排」，
  但「没配凭据」「接口超时」「返回空」「返回结构不对」四种原因被压成同一个值，
  失败原因只进了 logger。线上排查「重排怎么没生效」得翻日志，
  库里那张表回答不了。
- **重排的候选池固定 8 条**（`RERANK_CANDIDATES`），而且**重排只能修正池内顺序**，
  池外的召回不到。也就是说重排救不了「压根没进候选池」的用例——
  语义改写那 5 条的收益来自候选池够大 + 融合够全，不是重排无所不能。
- **语义改写用例只有 5 条**，「Top-1 +40pp」是 5 条样本上的统计，
  **置信区间很宽**，别当成「重排稳定提升 40%」来汇报。用例集扩大后这个数会变。
- **流量挖掘的标签是弱标签，但已经量化过了**：16 条真实感问句上，
  自动标注 7 条**全对**（100% 准确、43.8% 覆盖），其余进人工队列。
  换句话说它能保证"标的时候标对"，但**保证不了"都标到"**——
  词面不一致的问句（用户说涨薪、文档写调薪）它只能拒标。
  阈值 0.25 是 16 条样本上量出来的，真实流量积累后要重新校准。
  复核后并进 `chunk_cases.json` 目前得手改 JSON，没有回写/去重/合并工具。
- **仍然没有真实生产流量数据**：上面那 16 条是按真实问句的脏度手写的
  （口语化、错别字、省略主语、闲聊），不是真流量。
  工具在**真实**数据上的表现仍未验证——真实问句比手写的还脏
  （错别字更多、长句更多、同义不同词更多）。
- **CI 的 `--vector` / `--rerank` lane 仍没在真实 GitHub runner 上跑过**：
  已在**本机按 CI 的形态复现过**（清掉 `.env`、只给环境变量，跑 ci.yml 里的原命令，
  18/18 用例通过、重排确实生效），workflow 结构与 secret 名也核对过；
  但真机上第一次跑仍可能因为仓库设置（secret 名、runner 环境）出问题。
  为此给两个 job 加了 **preflight**：secret 缺失时 1 秒内失败并点名变量，
  而不是跑几分钟再报一个看不懂的错误。手动 lane 第一次用之前先确认 secret 配了。
- **评测器现在会拦下"重排被静默跳过"**：传了 `--rerank` 却没重排成功时，
  报告里 `rerank_check` 会记下"请求了但没生效"并让整轮判失败（退出码 1）。
  原因是 GitHub 对未配置的 secret 传**空串**，空串会让重排客户端直接返回 None
  且不报错——原先那种情况下报告"全绿"，其实重排根本没跑过。
